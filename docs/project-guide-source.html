Table: a named collection of database records. Row: one record. id: its identifier. Foreign key: a reference to a related row. company_id: the company that owns a tenant record. Header: the overall document. Items: its individual lines. Journal: the official double-entry accounting record.

Insert creates a row; update changes a row; read displays/calculates existing information. Most reports read records without creating new financial transactions.

01 · HOW THE PROJECT WORKS

From a button to a database row

Vue page → Inertia request → Laravel route → validation and authorization → controller → business service → Eloquent/database transaction → response

Laravel 12 handles the backend. Vue 3 with TypeScript provides the interactive screens. Inertia connects those screens to Laravel controllers, so application navigation uses Laravel routes rather than a separate Vue Router. Tailwind styles the interface and Vite builds the frontend.

The current local app uses database/database.sqlite. PostgreSQL is supported for later deployment. Laravel Eloquent models represent tables; Form Requests validate input; policies and permission checks protect operations. Dedicated services centralize accounting, banking, memberships and subscription behavior.

FolderPurpose
resources/js/PagesDashboard and business screens: Documents, Contacts, Purchases, Accounting, Banking, Reports and Settings.
resources/js/ComponentsReusable tables, form fields, money displays, user forms and permission editor.

Two kinds of business records

Invoices and bills describe business documents. Journal entries and journal lines describe their accounting effect. Saving a draft document does not affect profit, payable or receivable ledger balances. Approval creates its posted accounting record. Paying a posted document creates a separate settlement journal.

A database transaction groups related changes together. If posting fails because an entry is unbalanced or the period is locked, its linked financial changes roll back together.

03 · COMPANIES

Company creation and isolation

Open the company selector to create or switch a company. companies holds its name, legal/contact details, currency, timezone, financial-year start, status and lock date. A user can belong to several companies through company_users.

What creating a company inserts

  1. One company row and an active Owner membership for its creator.
  2. Eight default chart accounts: operating bank, receivables, input tax, payables, output tax, owner equity, sales and expenses.
  3. A bank-account record linked to the operating-bank asset account.
  4. A general expense category and a zero-rate default tax definition.
  5. Independent invoice, bill and credit numbering sequences.
  6. A financial year beginning on the selected start date.
  7. A 14-day trial subscription using the first active platform plan, when available.

What switching changes

Switching stores the selected company_id in the authenticated session. With the current database session driver, the session payload is stored in sessions. Switching does not copy transactions between companies. The user opens a feature allowed by their role.

How access is checked

The SetCompany middleware verifies active membership and an active company. CompanyContext supplies the current company. Tenant models automatically filter queries and populate company_id on creation; they fail closed without context. Composite foreign keys tie children to parents in the same company. Permission checks still apply after membership is established.

Global reference tables include users, roles, permissions, currencies, exchange rates and subscription plans. A global user is shared, but their company roles and company records remain separate. PostgreSQL row-level security is not currently enabled.

Code: app/Services/Tenancy/CreateCompany.php; CompanyContext.php; CompanyHome.php; app/Http/Middleware/SetCompany.php; app/Models/TenantModel.php.

04 · PEOPLE AND ACCESS

Users, roles and permissions

Open Settings → Users & roles at /settings/users. An Owner or a user with users.manage can manage company access.

RecordWhat is stored

company_userscompany_id + user_id + role_id + is_active. One user has one membership/role per company.
roles / permissionsRole names and permission names such as invoice.approve or banking.reconcile.
role_permissionsDefault permission pairs for each shared role.
company_permission_overridesCompany + role + permission + allowed. Permission editing replaces the selected company's override set.

Creating a new account

Click New user, fill name, email, password/confirmation and role, then create. The backend validates a password of at least 12 characters with letters and numbers, hashes it, inserts the user and active membership, records an audit event and dispatches registration after commit. The user must verify their email. Existing emails cannot be overwritten; use an invitation for an existing account.

Role defaults

RoleDefault purpose
Owner / AdministratorAll seeded company permissions; Owner permissions cannot be reduced.
AccountantFinancial operations and reports, excluding company/user administration.
Sales ManagerSelected contact and invoice creation, editing, approval and send actions.
EmployeeView contacts and expenses; create paid expenses.

Choose a member's role and Active checkbox, then Save access. Only that company's membership changes. Deactivation retains global identity and historical attribution. The last active Owner is protected. Creation/reactivation and outstanding invitations count toward plan limits.

Invitations and authentication

Inviting someone

An invitation creates company_invitations with email, role, expiry and a hashed token. The UI shows the original private invitation URL once through session flash. It must be shared with the recipient; automatic invitation-email delivery is not currently implemented.

The recipient registers or logs in, verifies their email, then accepts the link. Acceptance checks email, expiry and prior use, creates membership, sets accepted_at and records audit history. Revoking deletes the unused invitation and records an audit event. Duplicate pending invites and invites to existing members are rejected.

Login, verification and password reset

Login reads the stored password hash and writes session state. Logout invalidates the session. Email verification updates users.email_verified_at; it does not create a special verification table. Password reset uses hashed tokens in password_reset_tokens and updates the user's password hash. Profile editing writes the global user's name/email; changing email clears verification. The profile cannot be deleted while it still has company memberships.

Platform administration

The users.is_platform_admin flag controls platform plan management and verified subscription payments. It is separate from an Owner's company role. Granting it is a trusted-server operation through php artisan ledger:admin EMAIL, never the user-creation form.

Code: CompanyUserController; CreateCompanyUserRequest; MembershipService; CompanyPermissions; PermissionController; Settings/Users.vue; Breeze Auth controllers; PlatformAdministrator command.

05 · CONTACTS

Customers and suppliers

Sales customers are stored in customers; purchase suppliers are stored in suppliers. Both carry company_id, name, email, phone, address, tax number and active/archived status. They are independent contact collections, not parent/child tables.

ActionStorage and effect
Create / editInsert/update the appropriate contact row and audit event. No journal is created.
ArchiveSet status to archived. Linked invoices/bills and historical rows remain.
CSV importValidate every row first; insert new name/email pairs in one transaction. Existing pairs are skipped.
Contact historyRead invoices where customer_id matches, or bills where supplier_id matches.
Posted balanceRead linked posted control-account journal lines, including payments, credits/refunds and reversals.
Excel exportRead company contacts and stream an XLSX file; no financial rows are inserted.

The contact CSV header is name,email,phone,address,tax_number. The current limit is 10,000 rows / 5 MB. Document history is server paginated.

A contact row has no stored “balance” column. The current UI balance is calculated from accounting records. A supplier's open balance is normally payable; a customer's open balance is normally receivable. An overpaid/credited customer can have a negative receivable balance.

06 · SALES

Sales invoices and receipts

1. Save an invoice draft

invoices stores the header: customer_id, invoice_number, issue_date, due_date, currency, status, subtotal, tax_total, total, paid_total, credited_total and notes. invoice_items stores one row per line with invoice_id, account_id, description, quantity, unit_price, fixed discount and tax snapshot. Numbering increments the company's invoice row in document_sequences. Status starts as draft; no journal is posted.

Calculation: line subtotal = round(quantity × unit_price − fixed discount). Tax = round(subtotal × snapshotted rate / 100). Total = subtotal + tax. Invoice totals are sums of line totals. Quantity and price support four decimal places; posted amounts are rounded to two decimals with BCMath.

2. Approve and post

The invoice must be a positive draft. A journal is inserted and posted; its ID is written to invoices.journal_entry_id, and status becomes approved.

Approval accountDebitCredit
Accounts receivableInvoice total—
Sales/revenue accounts—Before-tax line amounts
Output tax, when applicable—Tax total

3. Receive money

A customer receipt inserts payments with invoice_id, bank_account_id, amount, paid_at, reference, journal_entry_id, idempotency_key and request_hash. It creates a settlement journal: debit Bank; credit Accounts receivable. It increases invoice paid_total and sets partially_paid or paid. The amount cannot exceed the outstanding amount; the payment date cannot precede the invoice date.

Current outstanding balance = total − paid_total − credited_total. It is a computed property, not a separate stored column. A paid status may reflect settlement by money and credits together.

Code: DocumentController; DocumentService::create/approve/pay; Invoice and Document models; Documents/Create.vue and Show.vue.

Invoice editing, sending and voiding

Editing is restricted to drafts. The service replaces draft items, recalculates totals and updates the header while keeping its document number. Posted financial fields and items are protected from ordinary mutation.

PDF and email

A PDF download reads the invoice/customer/items/company and renders a file. It does not add a financial transaction or automatically insert an attachment row. Email dispatch queues SendInvoice after commit. The worker checks company permission again, obtains a cache lock, renders a PDF and sends it through Laravel mail. Successful processing changes approved → sent and writes an invoice.sent audit event. Local mail is logged; a real SMTP transport is needed for delivery.

Voiding

Only approved/sent invoices with no payments and no credits can be voided. The service adds opposite journal lines in a new entry, sets its reversal_of_id to the original journal, changes invoice status to void and logs the action. The original journal remains posted; reports include both entries at their respective dates. The original invoice retains its original journal link.

Statuses and repeat requests

The implemented lifecycle uses draft, approved, sent, partially_paid, paid and void. Overdue is derived from due date and unpaid balance rather than a persisted scheduled status. Customer receipts use an idempotency key plus request hash: an exact retry returns the existing receipt; changing its payload while reusing the key is rejected.

There is no separate “invoice history” table. The header, items, payment records, credit records, journal links and audit events together form history. Initial invoice sending is implemented; later resend workflows are not.

07 · PURCHASES

Where a purchase is stored

Supplier → bills → bill_items → approval journal → bill_payments → bank matching

1. Create a supplier bill

Open Purchases → Bills. Select a supplier and enter the document dates and lines. bills stores one header with supplier_id, bill_number, bill_date, due_date, currency, notes, draft status and totals. bill_items stores each line's bill_id, expense/asset account, quantity, price, discount and tax. The bill numbering sequence advances and an audit event is inserted. Saving a draft does not yet affect accounting.

2. Approve the bill

The approval creates journal_entries and journal_lines. The bill gets approved status and journal_entry_id.

Approval accountDebitCredit
Selected expense or asset accountsBefore-tax purchases—
Input tax, when applicableTax total—
Accounts payable—Bill total

Expense-account purchases affect profit; an asset-account purchase increases assets. The software records input tax when a configured rate applies. Tax treatment must be configured appropriately for your business; this guide documents code behavior.

3. Pay the supplier

Insert bill_payments, not customer payments. The row links bill_id, bank_account_id and journal_entry_id, with amount/date/reference and retry-protection fields. The settlement journal is debit Accounts payable; credit Bank. Update bills.paid_total and status. Partial payments keep an outstanding payable; full settlement reduces it to zero.

Code: DocumentService with kind bill; Bill/BillItem/BillPayment models; Documents pages; BusinessRecordsExport.

Purchase relationships and history

RelationshipMeaning
suppliers.id → bills.supplier_idOne supplier can have many purchase bills.
bills.id → bill_items.bill_idOne bill has one or more item rows.
accounts.id → bill_items.account_idThe line's purchase classification.
bills.journal_entry_id → journal_entries.idThe original approved purchase entry.
bills.id → bill_payments.bill_idOne bill can have several partial payments.
bill_payments.journal_entry_id → journal_entries.idEach supplier payment has its own settlement entry.
bank_accounts.account_id → accounts.idThe bank metadata points to the ledger asset account used for the payment.
Example: an approved supplier bill is 1,000 before tax plus 100 tax = 1,100. Its purchase journal debits purchases 1,000 and input tax 100, credits payables 1,100. Paying 400 creates one bill_payments row, debits payables 400 and credits bank 400. Bill paid_total becomes 400 and outstanding becomes 700.

Draft editing replaces bill items and recalculates its totals. Ordinary edits to posted totals are blocked. Voiding an unpaid, uncredited approved bill creates an opposite journal and changes its status to void. Payment is recorded against one bill at a time; multi-bill supplier-payment batches and supplier credit-note workflows are not implemented.

Do not also enter the same supplier bill as a direct expense. Bill approval already records the purchase; payment records settlement rather than a second purchase expense.

A bill PDF or Excel export reads existing bill data; it does not create another bill or journal. Bank statement imports are independent records that can later be matched against the payment's bank journal line.

08 · DIRECT EXPENSES

Expenses and categories

Open Purchases → Expenses for a direct already-paid expense, such as office supplies purchased immediately from the bank. This workflow posts immediately; it is not a draft supplier bill.

TableStored information
expense_categoriesName, optional parent_id for nested categories and account_id for an expense ledger account.
expensesCategory, bank, date, description, before-tax amount, tax rate/tax amount, payment method, posted status, journal link and idempotency key/hash.

A direct expense of 100 plus tax of 20 posts: debit expense 100; debit input tax 20; credit bank 120. Profit reduces by the expense amount, while bank reduces by the gross payment.

The service requires an expense category tied to an expense account and a bank in the company's base currency. Inactive taxes are rejected. The frontend supplies a retry key; an identical retry returns the prior expense, while a changed payload with the same key is rejected.

Open a listed expense to view amounts, category, bank, private receipts and its journal if you have accounting permission. Posted expense records are immutable through ordinary model updates. Expense edit/reversal and optional approval stages are not implemented. Nested category creation exists as a protected backend endpoint, with no dedicated category management page yet.

09 · CUSTOMER ADJUSTMENTS

Credit notes and refunds

Issue a credit note

A posted invoice can receive credits against its original lines. The request selects invoice_item_id and a positive amount before tax. The credit cannot exceed that line's remaining uncredited subtotal. Tax is calculated from the original line's snapshot; the final credit absorbs remaining tax rounding.

credit_notes stores invoice_id, credit_number, date, gross amount, reason, status and journal link. credit_note_items stores each credited invoice_item_id, account_id, description, before-tax amount and tax_amount. The credit sequence advances. Posting updates invoices.credited_total and settlement status.

Credit-note postingDebitCredit
Original revenue accountsCredited before-tax amounts—
Output taxCredited tax—
Accounts receivable—Gross credit amount

Refund money to the customer

A refund requires an unrefunded posted credit and an actual customer credit balance. It inserts customer_refunds linked to the credit note, bank and settlement journal, with amount/date/key/hash. Posting is debit Accounts receivable; credit Bank. The service reduces the related invoice's paid_total, and records audit history.

An invoice totals 120 and the customer pays 120. A credit for 24 makes its outstanding receivable −24. Refunding 24 reduces net paid_total from 120 to 96. Outstanding then becomes 120 − 96 − 24 = 0.

A credit date cannot precede its invoice; a refund date cannot precede the credit. Refund retries use idempotency checks. No independent draft approval screen for credit notes is implemented: the issue operation creates and posts the credit together.

Code: CreditService::issue/refund; CreditController; CreditNoteForm; Documents/Credits.vue.

10 · ACCOUNTING CORE

Accounts, journals and reversals

accounts is the chart of accounts, not user login accounts. Its code/name/type/parent define classification; system_key identifies control accounts; cash_flow_class is operating, investing or financing. Ledger balances are calculated from journal lines, not stored in a balance column.

journal_entries stores date, reference, status, created_by, source_type/source_id, posted_at and optional reversal_of_id. journal_lines stores entry_id, account_id, debit, credit and description. All are company-owned.

Posting rules

  1. Company membership and operation permission are enforced by protected routes.
  2. Posting must be outside locked/closed accounting periods.
  3. Each entry must contain at least two valid active-account lines from the same company.
  4. Each line has exactly one positive debit or positive credit.
  5. Total debits must equal total credits, using rounded decimal strings.
  6. Insert header/lines, mark posted and record audit within a transaction.

Manual journals and opening balances

Manual journals use the same JournalService. The UI posts directly; a separate draft-review workflow is not enabled. Opening balances can be entered as a balanced manual journal, for example debit bank and credit opening equity.

Reversals

Reversing a manual journal creates another entry with debit/credit swapped. The new reversal_of_id references the original entry; its date cannot precede the original date. Each entry can be reversed once. Automatic entries must be adjusted through the originating document workflow, preserving document/payment summaries.

Posted journal headers and lines cannot be silently edited/deleted through the application. PostgreSQL adds immutable/balanced-posting triggers; SQLite local testing relies on the application checks plus available relational constraints. Account types with existing history cannot change; system controls must remain active with their original type.

Code: JournalService; AccountService; JournalEntry/JournalLine models; ImmutableRecord/ImmutableWhenPosted traits; AccountingController.

11 · BANKING

Bank statements and reconciliation

A bank account is stored in bank_accounts and points to an asset row in accounts. Bank balances are the posted debits minus credits for that ledger account. Creating bank metadata alone does not create an opening balance.

Importing CSV transactions

The CSV columns are date,description,amount,reference. Import creates bank_transactions containing the bank link, signed amount, transaction_type, reference, imported_at and import_hash. Positive amounts are receipts; negative amounts are payments. A fingerprint of date, amount, description and reference prevents duplicate rows for the same bank/company. Identical legitimate lines need distinct references. Zero-value lines are rejected.

Importing a statement does not create journal entries. The statement records what the bank reports; posting records what the books contain. Reconciliation connects the two.

Matching an imported row

Select an existing posted bank journal line. The line must belong to the imported transaction's bank ledger account, and its signed debit-minus-credit amount must exactly equal the statement amount. Neither transaction nor line may already be matched.

A successful match inserts reconciliations with bank_transaction_id, journal_entry_id, journal_line_id, matched_amount, status and reconciled_at, plus an audit event. It does not recreate the payment. Match state is determined by the reconciliation row rather than updating a special status column in bank_transactions.

Statement sessions

reconciliation_sessions stores bank_account_id, statement_date, closing_balance, status and closed_at. Closing verifies that all eligible imported transactions through that date are matched and the posted bank balance agrees with the statement's closing amount. The session is marked closed and audited.

The current matching operation does not populate session_id on reconciliations. Sessions certify the bank's complete eligible history through the end date; independent session allocation, split/group matches, undo and live bank feeds are not implemented.

Code: ReconciliationService; SessionService; BankingController; BankAccountController; BankSetup.vue.

12 · REPORTING

Dashboard and financial reports

Dashboard cards and charts read the active company's actual records. Revenue, expenses and profit are derived from posted journal lines; bank balances use bank-linked accounts. Outstanding invoice/bill summaries use document totals minus settlement/credits. Recent/overdue/upcoming lists read company documents. Reports do not need their own “report transactions” table.

Trial BalanceGroup posted debits/credits by account for the selected range. Displayed balance is debit − credit; the current screen is period movement.
General LedgerPosted journal lines with account/entry metadata; paginated and filterable.

Customer StatementsInvoice-linked receivable journal lines, receipts, credits, refunds and reversals; opening/running/closing balance.

These are operational reports; jurisdiction-specific statutory statements and tax filings require additional configuration/design.

13 · FILES AND HISTORY

Attachments, exports, queues and audit

Private attachments

attachments stores company_id, model_type, model_id, disk, path, filename, MIME type and size. The binary is stored on the configured private filesystem, not inside the row. model_type is invoice, bill or expense; model_id points to that corresponding row. This polymorphic reference is validated by application logic rather than a generic SQL foreign key to three different tables.

Uploads support PDF/JPG/PNG/WebP up to 10 MB. Downloads check active tenant ownership and record permission. Paths are under company-specific attachment folders. Local storage is used now; private S3-compatible storage is available through configuration.

Report and business exports

Contact/invoice/bill XLSX exports and most PDF/report exports are generated synchronously from existing data. General-ledger/account-transactions PDF or XLSX requests create report_exports and enqueue GenerateReportExport. The record stores requesting user, company, report, format, filters, disk, path and queued/processing/ready/failed state. Generated binaries live under the company's private exports folder. Downloads recheck ownership and report permission. Spreadsheet cells are treated safely as strings to prevent formula injection.

Queue infrastructure

The local database queue stores pending work in jobs. A worker handles emails and exports. Completed queue rows are removed; failed_jobs tracks failures, and job_batches is available for Laravel batching. Local database cache/locks use cache and cache_locks. Redis/Horizon is prepared for Linux deployment; Horizon metadata is held in Redis rather than tenant accounting tables.

Audit trail

audit_logs records company, optional actor user, event, model class, record ID, JSON old/new values and timestamp. It records important financial, membership, permission and reconciliation actions. Some background actions have a null actor when no authenticated user is set; journal posting can pass an explicit actor. The log is not a complete version snapshot of every database change. Eloquent and PostgreSQL protect it against modification; access to its screen requires management permission.

15 · SAAS BILLING

Subscriptions and platform plans

subscription_plans → subscriptions → subscription_invoices → subscription_payments

SaaS billing describes what a company pays to use Ledger. These records are separate from the company's customer invoices and supplier purchases.

Plans and company subscriptions

subscription_plans holds name, description, price, currency, monthly/yearly interval, JSON features/limits and availability. Platform administrators manage plans at /admin/plans.

subscriptions links company_id to plan_id with status, start/end date, trial_ends_at, cancelled_at and price/currency snapshot. A company's first subscription starts a 14-day trial. Selecting the same current plan returns it; changing plan cancels the prior record and creates a new full-price period. Proration is not implemented. Plan changes are blocked while the current subscription is past due.

Billing invoices and renewal

subscription_invoices stores subscription_id, number, amount, currency, due_date, period_start/end and open/paid status. Renewal uses a unique period-start key to prevent duplicate billing rows. A scheduled command processes due subscriptions under company context. Open overdue invoices mark the subscription past_due and block creating new restricted records. Invoice/member limits are enforced on relevant backend operations.

Verified platform payment

A platform administrator records a verified provider/reference value. The service inserts subscription_payments, marks the subscription invoice paid and reactivates a past_due subscription. It does not reactivate a cancelled plan. Reusing a reference for the same invoice returns the prior payment; using it for a different invoice is rejected.

No tenant journal is posted for SaaS billing. An external card gateway, automatic recurring charge and provider webhook verification are not implemented. The payment action records a payment already verified by the platform administrator.

Follow a purchase through the tables

These IDs and amounts are illustrative. The example uses company 10, supplier 20, bank 30, bill 40 and a 10% tax rate.

Payment 400journal_entries row 51 debits payables 400 and credits bank 400. bill_payments references bill 40, bank 30 and journal 51. bills.paid_total becomes 400; status partially_paid; outstanding 700.
Receipt attachmentattachments model_type bill/model_id 40; file binary stored privately.

Which rows would a second payment create?

Paying the remaining 700 creates another bill_payments row and another settlement journal. It does not create another bill or another purchase-cost entry. Total paid becomes 1,100, outstanding becomes zero and bill status becomes paid.

A sale follows the mirror workflow

Customer → invoice/items → approval debits receivable and credits revenue/output tax → payment debits bank and credits receivable → statement match. A credit reduces original revenue/tax/receivable; a refund clears an existing customer credit using the bank.

Inspecting and running the project

Where to inspect local data

Use a SQLite database viewer to open database/database.sqlite. Start with the document header, follow its item rows, then its journal_entry_id and journal_lines. Always filter by company_id: IDs alone are not a company boundary. The examples below are read-only SQL queries; replace 10 and 40 with your selected company and bill.

SELECT * FROM bills WHERE company_id = 10 AND id = 40;

SELECT * FROM bill_items WHERE company_id = 10 AND bill_id = 40;

SELECT * FROM bill_payments WHERE company_id = 10 AND bill_id = 40;

SELECT * FROM journal_lines WHERE company_id = 10
AND journal_entry_id = (SELECT journal_entry_id FROM bills
WHERE company_id = 10 AND id = 40);

For a reversal, inspect journal_entries where reversal_of_id equals the original journal ID. For an imported bank match, inspect reconciliations by bank_transaction_id. For report totals, only posted journal entries qualify.

The project contains connected accounting workflows, not a static dashboard. At the same time, the original production-oriented brief is broader than the currently delivered functionality. This guide distinguishes those boundaries.

Storage concepts worth remembering

  • User accounts live in users; ledger accounts live in accounts.
  • Customer money receipts live in payments; supplier money payments live in bill_payments.
  • Tenant sales invoices live in invoices; SaaS platform charges live in subscription_invoices.
  • Business document details live in item tables; official debit/credit movements live in journal_lines.
  • Imported bank records do not automatically create accounting postings.
  • Files live on private storage; attachments/report_exports store metadata and paths.
  • Most balances, dashboard cards and reports are calculated rather than stored in separate total tables.
